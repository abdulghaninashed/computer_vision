# نظام مراقبة وتحليل حركة المرور

## About

مشروع رؤية حاسوبية لتحليل فيديو حركة المرور وتتبع المركبات وعدّها عند عبورها خطًا محددًا. يعرض التطبيق الفيديو والإحصائيات في واجهة ويب محلية، ويصدر تقريرًا بعدد المركبات المسعّرة وإيراداتها، ويرسل إشعارات المخالفات إلى بوتات تيليغرام بحسب اتجاه المركبة.

## Setup & Run

### المتطلبات

- Python و`pip`.
- ملف أوزان النموذج `models/best(9).pt`. الأوزان غير مضمّنة في Git لأن مجلد `models/` مستثنى في `.gitignore`؛ ضع الملف في هذا المسار قبل التشغيل.

### تثبيت وتشغيل التطبيق

نفّذ الأوامر من مجلد المشروع الرئيسي. أنشئ بيئة افتراضية:

```bash
python -m venv .venv
```

فعّل البيئة:

```bash
# Linux أو macOS
source .venv/bin/activate

# Windows PowerShell
.\.venv\Scripts\Activate.ps1
```

ثبّت المكتبات المطلوبة ثم شغّل التطبيق:

```bash
python -m pip install -r requirements.txt
python src/main.py
```

يفتح التطبيق على `http://127.0.0.1:5000`. اختر فيديو بصيغة MP4 أو AVI أو MOV أو MKV ثم اضغط **بدء التحليل**. يمكن تعديل خط المنتصف من الإعدادات، وإيقاف التحليل مؤقتًا واستئنافه. يعرض زر **التقرير** جدول المركبات والإيرادات. عند الضغط على **إيقاف** يعرض تقرير الجلسة ثم يصفّر العدّادات بعد انتهاء التتبع.

### إعداد إشعارات تيليغرام للشرطة

لإعداد بوتي الذهاب والإياب مرة واحدة:

1. انسخ `.env.example` إلى ملف جديد اسمه `.env` في مجلد المشروع الرئيسي.
2. افتح `.env` واستبدل القيم التجريبية برموز البوتات ومعرّفات المحادثات. استخدم `@First_Police_TrackingBot` للذهاب و`@Second_Police_TrackingBot` للإياب.
3. احفظ الملف وشغّل التطبيق كالمعتاد.

**ملاحظة مهمة عن اسم الملف:** يقرأ الكود ملفًا اسمه `.env` من جذر المشروع. ملف `.env.example` قالب توضيحي فقط ولا يُقرأ تلقائيًا؛ يجب نسخه يدويًا وتسميته `.env`. أُضيف `.env` إلى `.gitignore` كي لا تُرفع الرموز السرية إلى Git، بينما يجب أن يبقى `.env.example` خاليًا من الأسرار.

توجّه مخالفات الذهاب إلى إعدادات بوت الذهاب، ومخالفات الإياب إلى إعدادات بوت الإياب. يرسل النظام إشعارًا مرة واحدة لكل مخالفة لكل مركبة متتبعة خلال الجلسة: الدراجات النارية والسيارات التي تتجاوز حد السرعة البرمجي. سرعة السيارة في الإشعار تقديرية بالبكسل/ثانية وليست كم/ساعة. إذا لم تُضبط متغيرات أحد الاتجاهين، يسجل التطبيق خطأً ولا يرسل الإشعار.

## Documentation

### آلية عمل المشروع

1. يحمّل التطبيق نموذج YOLO من `models/best(9).pt` ويعالج إطارات الفيديو باستخدام Ultralytics وOpenCV.
2. يستخدم التتبع المستمر `ByteTrack` للاحتفاظ بمعرّف كل مركبة بين الإطارات.
3. يعتمد العدّ على عبور أسفل صندوق المركبة خطًا أفقيًا عند 75% من ارتفاع الإطار. يُحتسب معرّف التتبع مرة واحدة في الجلسة.
4. يحدد موضع المركبة بالنسبة إلى خط المنتصف اتجاهها: يسار الخط ذهاب، ويمينه إياب.
5. تسعير التقرير: السيارة 1$، الفان 1.5$، الشاحنة 2.5$، والباص 2$. إجمالي المركبات يشمل المركبات المكتشفة؛ أما الإيراد فيُحسب للفئات الأربع المسعّرة.

### البيانات والتدريب

بحسب دفتر التدريب الموجود في `train_in_colab/finally_trainning.ipynb`، اعتمد التدريب على مصدرين:

- مجموعة مخصصة من Roboflow، المشروع `abdulghani`، الإصدار 4، مع نسخ أقسام التدريب والتحقق والاختبار الموجودة.
- مجموعة COCO، مع اختيار فئات `motorcycle` و`car` و`truck` و`bus` ودمج الصور التي تحتوي على كائنات من هذه الفئات مع بيانات Roboflow. يعيد الدفتر ترقيم الفئات لتتوافق مع ترتيب فئات Roboflow.

تتضمن الفئات المطلوبة في إعداد Roboflow: `car` و`motorcycle` و`truck` و`bus` و`van` و`policemotorsycle`. ويسجل ناتج التدريب استخدام 10,791 صورة تدريب و955 صورة تحقق بعد تجهيز البيانات.

بدأ التدريب من أوزان YOLO11n المسبقة التدريب، باستخدام 25 حقبة، وحجم صورة 640، ودفعة 16. حُدد المحسّن `AdamW` ومعدل التعلّم `0.001`، مع `patience=15`، واختيار GPU عند توفر CUDA وإلا استخدام CPU. خيار تجميد أول 10 طبقات موجود في الدفتر لكنه معلّق، لذلك لم يُفعّل في هذا التدريب.

تظهر في إعدادات التدريب المسجّلة Mosaic بقيمة 1.0، والقلب الأفقي بقيمة 0.5، وتغييرات HSV، والمقياس والإزاحة، مع إغلاق Mosaic في آخر 10 حقب. هذه إعدادات مسجلة من Ultralytics في ناتج التدريب، وليست مرحلة تكثير بيانات منفصلة ينفذها الدفتر.

### التحديات الفنية وطريقة التعامل معها

#### إنشاء مجموعة بيانات للفئات الست

كان من أكبر التحديات إعداد مجموعة بيانات تضم الفئات الست المطلوبة. عثر الفريق على مجموعة بيانات لفئة `van`، لكن العثور على مجموعة جاهزة لفئة الدراجات النارية التابعة للشرطة (`policemotorsycle` في إعداد الفئات) كان صعبًا. ساعدت فيديوهات وزارة الداخلية التي تظهر أرتالًا من دراجات الشرطة في توفير أمثلة لهذه الفئة.

#### النسيان الكارثي عند التدريب

أثناء التدريب، لاحظ الفريق أن النموذج ينسى بعض ما تعلمه من بيانات COCO، فتراجع كشف السيارات والشاحنات. كان الحل الذي اعتمده الفريق دمج بيانات Roboflow مع أمثلة فئات COCO المطلوبة ضمن مجموعة التدريب، بدل تدريب النموذج على بيانات Roboflow وحدها.

نوقشت حلول أخرى، منها تجميد بعض طبقات النموذج، أو استخدام نموذجين بالتتابع لكل منهما مجموعة فئات مختلفة ثم دمج نتائجهما؛ لكن هذا النهج قد يؤدي إلى تضارب بين الكشفين. كما طُرح فصل مكوّنات `backbone` و`neck` ودمجها في `head` واحد، لكن لم يُبحث عمليًا في كيفية تطبيق هذا الخيار، لذلك لم يُعتمد ضمن الحل المنفذ.

#### تحديات العدّ والتطبيق

- **منع تكرار العدّ:** قد يظهر الجسم نفسه في إطارات كثيرة؛ يستخدم التطبيق معرّفات ByteTrack ومجموعة للمركبات التي عُدّت.
- **تحديد لحظة العبور والاتجاه:** يحتفظ التطبيق بموضع المركبة بين الإطارات ويقارن عبورها بخط العدّ، ثم يستخدم خط المنتصف لتحديد الاتجاه.
- **التحكم بالمعالجة:** يعمل التتبع في مسار منفصل عن خادم الويب، مع دعم الإيقاف المؤقت والاستئناف والإيقاف النهائي.
- **عرض التحليل والتقرير:** يرسل الخادم الإطارات والإحصائيات إلى واجهة ويب محلية، ويجمع التقرير الأعداد حسب الفئات المسعّرة.

### نقاط الضعف والقيود المعروفة

- ملف الأوزان المطلوب غير مضمّن في Git؛ لن يعمل التطبيق على نسخة جديدة حتى يوضع `best(9).pt` يدويًا في `models/`.
- يعتمد العدّ على جودة الكشف والتتبع. قد يؤثر الحجب أو فقدان معرّف المركبة بين الإطارات في النتيجة.
- تعرض السرعة كتقدير بالبكسل/الثانية اعتمادًا على موضع المركبة ومعدل إطارات الفيديو؛ لا تمثل كم/ساعة فعلية. يُعدّ الجسم سريعًا إذا بلغت سرعته 40% من عرض الإطار في الثانية، ويحتاج تحويلها إلى سرعة واقعية إلى معايرة المشهد.
- لا توجد أسعار محددة في التقرير للدراجات النارية أو أي فئات أخرى خارج السيارة والفان والشاحنة والباص؛ تدخل في إجمالي المركبات، ولا تدخل في الإيراد.
- يعتمد اتجاه الحركة على موضع المركبة بالنسبة إلى خط المنتصف، وليس على اتجاه عبور الخط الأفقي وحده.
- لا يتضمن المستودع حاليًا مجموعة اختبارات آلية موثقة.
